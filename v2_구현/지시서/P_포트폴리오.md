# 지시서 P: 기획 포트폴리오 정리

> 먼저 `v2_구현/지시서/00_공통.md`를 읽어라. 앞 단계: **G 밸런스**가 끝나 있어야 한다. W와 함께 진행해도 된다.
> **이 작업은 사용자(게임 기획자)의 포트폴리오다.** 결정의 주인은 사용자다. 문서에 쓰는 결정과 이유는 모두 기록에 근거해야 하고, 지어내지 마라. 기록에 이유가 없으면 「(이유 확인 필요)」라고 표시하고 보고에 모아라.

## 목표
채용 담당자(게임 기획 직군)가 **10분 안에** 다음을 알 수 있게 한다.
1. 무슨 게임인가: 컨셉, 핵심 재미, 한 판의 흐름
2. 어떻게 설계했는가: 문제 → 레퍼런스 조사 → 대안 → 결정 → 검증(시뮬, 평가) → 반복
3. 해 볼 수 있는가: itch.io 링크(W)

## 재료 (읽을 것)
- `결사_기획서.md`: 1~19장. v1부터의 설계 기록과 v2 구상
- `v2_구현/*.md`: 단계별 설계 문서, 조사 문서, 밸런스 결과, 12단계(외부 평가 반영)
- `결사_규칙서_v2.html`: 지금 규칙
- `로드맵_v1.2_v2.md`, `품질개선_계획.md`, `플레이테스트_가이드.md`, `보드게임_레퍼런스_브레인스토밍.md`
- `git log --stat`: 언제 무엇을 바꿨는지(타임라인)
- `game/tools/v2_balance.gd` 결과: 그래프로 만들 수치

## 만들 것 (`portfolio/` 폴더, HTML, 인쇄하면 PDF로 깔끔하게)
### 1. 한 장 소개 (`index.html`)
- 제목, 한 줄 컨셉, 스크린숏 1장, 「브라우저에서 하기」 링크(자리만 두고 사용자가 채움)
- 핵심 재미 3개. 예: 큰 눈을 이동과 판정 중 어디에 쓸지, 1막에서 첩보를 모아 2막 대상을 고름, 일제 동향
- 하루의 흐름 그림(아침 → 낮 → 밤)과 두 막 구조 그림
- 내 역할과 제작 방식(아래 4절)

### 2. 설계 사례 (`cases.html`)
5개 안팎. 사례마다 같은 틀로 쓴다:
- **문제:** 어떤 플레이 상황에서 무엇이 재미없었나
- **근거:** 시뮬 수치, 플레이 관찰, 외부 평가
- **레퍼런스:** 조사한 게임과 거기서 가져온 것
- **대안:** 검토한 것과 버린 이유
- **결정**
- **결과:** 바뀐 수치나 플레이

후보 (기록을 보고 고르고 순서를 정해라):
1. 아침 팀 주사위 → 개인 작전 주사위(Dead of Winter): `조사_아침주사위_대안.md`, 7단계
2. 미션을 타일에서 떼어 마커로, 미션 여섯 종류: `조사_미션_레퍼런스.md`, 8단계
3. 변절을 넣었다가 뺀 결정. 「언덕 위의 집의 배신」 등을 조사했고, 9단계에서 뺐다. **뺀 결정도 좋은 사례다.**
4. 「주사위 1개 = 행동 1개」 행동 제한: 11단계
5. 외부 평가를 받고 반영한 과정. 문제 3개 → 일제 동향, 같은 칸 허용, 반격: 12단계
6. 밸런스: 시뮬로 승률과 결행 대상별 차이를 맞춘 과정(G)

### 3. 밸런스 보고 (`balance.html`)
- 그래프:
  - 승률의 변화(단계별)
  - 결행 대상별 승률
  - 요원별 승률
  - 엔딩 분포
  - 결행한 날 분포
- 그래프는 수치를 HTML 안에 넣어 그린다. 외부 라이브러리는 CDN 하나까지만 쓴다.
- 목표와 결과, 남은 문제

### 4. 내 역할과 제작 방식
- 사용자가 한 일(컨셉, 규칙 설계, 결정, 레퍼런스 조사 방향, 평가 반영 판단)과 도구가 한 일(구현, 시뮬, 문서 정리)을 **정직하게** 나눠 적는다.
- AI 도구로 구현을 도왔다는 사실은 숨기지 않는다. 기획자 포트폴리오에서는 **설계 판단이 내 것**이라는 게 핵심이다.
- **이 절은 초안만 쓰고, 사용자가 직접 고치도록 보고에 표시해라.**

### 5. 규칙서
- `결사_규칙서_v2.html`을 `portfolio/rules.html`로 연결한다. 맨 뒤 「개발 메모」는 포트폴리오판에서는 숨긴다.
